# Tasks — cap the re-sent conversation

## 1. Capping module

- [x] 1.1 New `src/agent/history.ts` with `capHistory(messages, opts)` returning `{ messages, stats }`, plus `HISTORY_CAP_DEFAULTS`. Builds a structurally independent view; the caller's array and message objects are never mutated (D1, D3b). Verified: `test/history-cap.test.ts` ("never mutates the caller's array").
- [x] 1.2 Preserve length, order, roles, and `toolCallId` exactly; shrink only content and oversized argument strings (D2). Verified: `test/history-cap.test.ts` ("preserves length, order, roles, and tool-call ids exactly"), which also renders through `renderDelta` at the resume index to prove the session-resume slice still lands.
- [x] 1.3 Supersede a `read_file` result when a later read of the same path *covering its line span* exists, at any distance; never supersede the newest read of a path (D3, D3a). Verified: six tests — supersession fires, the newest read survives in full, different paths stay independent, a partial later read does not supersede a whole-file read, disjoint ranges do not supersede, and a wider later read does supersede a narrower earlier one.
- [x] 1.4 Head-and-tail clip oversized tool results and tool-call argument strings, outside the recent window only, each with an in-band marker (D4). Verified: two tests asserting head/tail retention, the marker text, and that short arguments (`path`) pass through untouched.

## 2. Wiring

- [x] 2.1 Cap at the `provider.chat` call site in `src/agent/loop.ts`, sending the capped view while keeping `messages` whole for the transcript and the next turn's pass. Verified: `npm run typecheck` + full suite green (592 passed).

## 4. Tests

- [x] 4.1 Invariants: length/order/role/id parity, no caller mutation, short conversations returned untouched.
- [x] 4.2 Behavior: supersession (fires, newest survives, path-independent), result clipping, argument clipping, recent window left verbatim.
- [x] 4.3 End-to-end shrinkage through `renderConversation`, and a realistic schematic-stage fixture on the real defaults. **This test found a real design flaw**: with the recent window protecting *all* trims, capping barely fired, because the window was shielding the largest and most recent schematic re-reads. Fixed by D3 (supersession ignores the window, truncation respects it). Measured after the fix: 260,134 → 71,105 rendered chars, a 72.7% reduction (~47k tokens) on one turn, message count unchanged.

## 6. First review round

- [x] 6.1 **Supersession ignored line ranges (real bug).** `read_file` honours `start_line`/`end_line`, so a later twenty-line read does not reproduce an earlier whole-file read, yet supersession matched on path alone and dropped the earlier result. Found in review. Fixed by recording each read's span (absent bound meaning end-of-file, so a whole-file read is `[1, Infinity]`) and superseding only when some later read of the same path contains that span (D3a). Verified: three new tests for partial, disjoint, and covering reads. Proposal, design, and the delta spec updated alongside.
- [x] 6.2 **`clip` could grow a barely-oversized value.** The elision marker was appended *after* filling the cap, so a value one character over the limit came back longer than it went in and `charsSaved` went negative, making capping increase the request. Found in review. Fixed by reserving the marker's length inside `max` (using the largest count it could print, so the reservation is never short) and leaving the value whole when the cap cannot hold a marker plus content. Verified: two new tests (never grows, never reports a negative saving; tiny cap leaves the value intact).
- [x] 6.3 **Unsettled tool-call arguments could be clipped.** Argument truncation is justified by the call having already run, but nothing checked for a matching result. Found in review. Fixed by collecting settled `toolCallId`s from `tool` messages and clipping only those calls' arguments. Verified: new test that a call with no result keeps its payload intact even well outside the recent window.
- [x] 6.4 **The short-history path returned the caller's own array.** That broke the documented request-view contract: a provider mutating what it was handed would have reached the run's history. Found in review. Fixed by returning a shallow copy. The existing identity assertion was inverted to match the contract rather than the old behavior.
- [x] 6.5 **`capCharsSaved` under-reported retried requests.** The capped view is built once but `withRetry` can put it on the wire several times, while the saving was counted once. Found in review. Fixed by counting inside the retry callback, so the figure measures characters actually kept off the wire, and emitting one `history-capped` event per attempt carrying its attempt number. Verified: new loop-level test that rate-limits a turn once and asserts the run total reflects both attempts.
- [x] 6.6 **`capCharsSaved` was recorded but never rendered.** `renderRunStats` omitted it, so `summary.md` hid the saving. Found in review. Fixed by adding a line to the run-stats block, omitted when the value is absent.

## 7. Second review round

- [x] 7.1 **A failed read could supersede a successful one.** `dispatchTool` catches a throwing handler and returns `error: <message>` as an ordinary tool result, so a `read_file` that failed (missing path, outside the repo) is shape-identical to one that succeeded and was being recorded as a supersession candidate. It would then replace real file content with a stub pointing at a read that returned nothing. Found in review. Fixed by excluding failed results from the candidate set. Verified: new test that an `error: ENOENT` result leaves the earlier successful read intact. Superseded by 7.5, which replaced the prefix test used here with a real status flag.
- [x] 7.2 **`rangeOf` mis-modelled `end_line` without `start_line`.** Found while checking 7.1 against the tool rather than the schema: `toolReadFile` returns the whole file whenever `start_line` is absent, ignoring `end_line`, but the read was recorded as `[1, end_line]`. That understates what the model received and would let a later, genuinely narrower read supersede it. Fixed by treating an absent `start_line` as a whole-file read. Verified: new test.
- [x] 7.3 **The view shared message objects with the run's history.** A fresh array is not enough: a provider mutating a message's `content`, or a tool call's `args`, in what it was handed would write straight into the history the transcript and the finish gate read from. Found in review. Fixed by returning fresh message objects, tool-call arrays, and argument objects (D3b). Costs object shells only, since strings are immutable and shared by reference. Verified: new test that mutates every level of the returned view and asserts the input is untouched.
- [x] 7.4 **The retry test never inspected what was sent.** It asserted `capCharsSaved` only, so it would have passed had the loop computed the saving from capped history while sending the uncapped array. Found in review. Fixed by recording each request in the scripted provider and asserting, on both rate-limited attempts, that the superseded stub is present, the newer read survives in full, and message count, roles, and `toolCallId` order are intact. Also raised the test's turn budget: at `maxTurns: 6` the loop injects its "only 5 turns remain" nudge, which adds a message and confounds the identity assertions.
- [x] 7.5 **Failure was inferred from the result text.** 7.1 excluded failed reads by testing for `error:` and `tool "` prefixes, which misclassifies a successful read of a file whose contents genuinely begin that way (a build log, a pasted traceback). Found in review. The consequence was conservative (lost savings, never lost content), but the fix removes the guess rather than narrowing it: `dispatchToolResult` now returns `{ text, ok }`, the loop records `failed` on the tool message and on the transcript event, and capping reads that flag instead of the text. The string-returning `dispatchTool` is kept as a thin wrapper, so its many call sites are untouched (D3c). Verified: unit test that a file whose contents start with `error:` still supersedes normally, plus a loop-level test running one succeeding and one genuinely failing read and asserting only the latter is flagged.

## 8. Third review round (coverage-only, no production change)

- [x] 8.1 **`historyCap: false` was never exercised by any test.** Branch coverage showed the `config.historyCap ? capHistory(messages) : { messages, stats: null }` ternary's disable arm (`loop.ts:526`) had zero hits, and no test supplied `historyCap: false` in a config file, so `config.ts`'s `raw.historyCap !== false` parsing was untested in the direction that matters. Found in review. Confirmed as a real gap, not a bug: added a `config.ts` unit test (`loadConfig` turns `{ historyCap: false }` into `config.historyCap === false`) and a loop-level test that runs a turn with capping disabled and asserts the provider received the two reads of the same file in full, with no superseded stub. Verified the test is a real regression check, not a rubber stamp: reverting the ternary to always call `capHistory` makes it fail.
- [x] 8.2 **The open-ended `start_line`-with-no-`end_line` range was untested.** Every existing range test supplied both bounds, leaving `rangeOf`'s `: Infinity` fallback (`history.ts:121`) uncovered — a legitimate `read_file` usage (`read_file` itself supports an omitted `end_line`). Found in review. Added a test asserting an open-ended read is *not* superseded by a later bounded read that doesn't reach EOF, and *is* superseded by a later whole-file read. Verified as a real regression check: capping the fallback at `{ start: s, end: s }` instead of `Infinity` makes the test fail.

## 10. Fourth review round (two mediums, seven lows)

- [x] 10.1 **The delta spec stated a rule the shipped defaults violate.** `specs/agent-core/spec.md:37` claimed "The most recent read of a path SHALL always be sent in full", but being newest protects a read from *supersession* only: with both reads below `truncateBefore` the earlier is stubbed and the newest is clipped, so the file is fully present in neither. `design.md` D3 already documented the composition correctly, so the delta spec was the stale artifact and would have merged a false requirement into `openspec/specs/` at archive time. Found in review. Corrected the sentence and the scenario, and added a test on the exact shape (two whole-file reads plus 20 filler messages under real `HISTORY_CAP_DEFAULTS`) asserting the earlier is stubbed *and* the newest is truncated. No production change: the code was already right.
- [x] 10.2 **Capping invalidated the Anthropic prompt-cache prefix.** Rewriting an arbitrarily old message diverged the request from the cached prefix, and the only breakpoints at or below it were the system prompt and the last tool definition, so the whole conversation was re-billed at 1x input plus a 1.25x cache write on exactly the turns capping exists to make cheaper. Found in review. `capHistory` now reports `firstChanged` (the lowest index it rewrote), the loop forwards it as `ChatOpts.stablePrefixBefore`, and `AnthropicProvider` places a fourth `cache_control` breakpoint on the last block below that index — four being Anthropic's maximum. Recorded as design D7.
- [x] 10.3 **`clip` split surrogate pairs.** Slicing by UTF-16 code unit put lone surrogates into the request when an astral-plane character straddled the head or tail cut. Found in review. Both cuts now snap off a surrogate boundary; a regression test sweeps an emoji across both cut offsets and fails at offset 2328 without the fix.
- [x] 10.4 **`capCharsSaved` counted requests that were never sent.** The counter fired before `provider.chat` and even on an llm-cache replay, so a fully replayed stage printed a saving beside zero tokens. Found in review. Accounting moved after the call and skipped on a replay via a new `Turn.cached` flag, while deliberately still counting a rate-limited attempt (those bytes did go over the wire) — which is why it sits in a `finally` rather than on the success path. Summary line reworded to "characters trimmed from the request view", which stays true under session resume too.
- [x] 10.5 **`Msg.failed` promised more than it delivered.** `ok: true` means only "the handler did not throw", so handlers returning a rejection string (`edit_file`'s "edit REVERTED", `finish`'s "cannot finish yet", the U+FFFD rejection) were recorded as successes. No functional impact — `read_file` supersession is the only consumer and every real `read_file` failure throws — so the doc comment was narrowed to "the handler threw" rather than widening the classification for no caller.
- [x] 10.6 **A test assertion could not detect the regression it named.** `expect(renderConversation(out)).toContain(sch.slice(0, 200))` is satisfied by a clipped result too, since `clip` keeps a 60% head. Replaced with a full-length assertion plus the absence of an elision marker on the newest read's own message.
- [x] 10.7 **A default-on change to what every provider is sent had no acceptance criterion.** Added AC-3.21 (capped conversation, identity preservation, `historyCap` escape hatch) and AC-3.22 (span accuracy) to `SPEC.md`, per the precedent that every other unarchived change carries its ACs there. Also added the two missing delta-spec scenarios (argument clipping, and the settled/unsettled rule), surfaced `historyCap` in `/config`, and hardened the REPL tests to tear the session down before deleting its repo and to assert against an exported `PROMPT`.

## 11. Fifth review round (four lows: one doc, two coverage, one guard)

- [x] 11.1 **D7's cost bound was wrong.** It claimed the monotone view means a message is rewritten at most once. A result *clipped* when it crossed out of `keepRecent` is rewritten a second time, to a stub, once a later read of the same path supersedes it — and re-reading a file is precisely this change's target workload, so that is the common path, not a corner. Found in review. D7 and the `firstChanged` doc comment now say "monotone *per trim kind*" and budget two partial misses for a re-read path. Added the note that the mitigation is Anthropic-only by necessity: OpenAI's prefix caching exposes no breakpoint control, and the session-resume providers send only the delta.
- [x] 11.2 **The fourth cache breakpoint — the whole of 10.2's fix — had no test**, and there was no `anthropic-provider` test at all though every sibling provider has one. Added `test/anthropic-provider.test.ts`: a stub `http` endpoint (SDK pointed at it via `ANTHROPIC_BASE_URL`, explicit test key, loopback only) captures the real request body and pins the breakpoint count *and* positions with and without `stablePrefixBefore`, including both degrade-to-three cases and the four-breakpoint ceiling. Verified as a real regression check: reverting the placement makes it fail.
- [x] 11.3 **The `!chatRes?.cached` skip was never exercised with `cached === true`**, and `CachingProvider` setting the flag was unasserted. Added an A/B loop test (the control run asserts a live turn *is* credited on the same script, so the replay's `toBeUndefined()` proves the skip rather than proving capping never fired) plus a direct `CachingProvider` test: a miss reports no flag with real usage, a hit reports `cached` with zero usage. Verified as a real regression check: removing the skip makes the loop test fail. Note `loop.ts` wraps in `CachingProvider` only when no provider is injected, so the flag has to be modelled in the loop-level test and pinned against the real class separately.
- [x] 11.4 **`await transcript.event` moved into a `finally`, where a rejection could mask the in-flight provider error.** On the path where `provider.chat` rejects with a 429 headed for `withRetry`, a failing transcript write (EACCES/ENOSPC under `.copperhead/runs/`) would propagate in its place and `withRetry` could not classify it as retryable. Guarded with `.catch(() => {})`: losing one accounting line beats masking the real failure. Regression test pins it by stubbing `Transcript.prototype.event` to reject on the `history-capped` event and asserting the run still retries the 429 and completes.
